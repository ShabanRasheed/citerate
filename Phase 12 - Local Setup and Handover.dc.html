Q2 · HOW DO I RUN IT LOCALLY
Two terminals, seven commands, no accounts

Nothing external is needed for a local run. Mocks stand in for the engines, magic links print to the console, and Cloudflare's always-passes test key covers Turnstile.

# terminal 1 — marketing repo. Its 0001 creates the base tables.
cd citerate
pnpm install
cp .env.example .env
pnpm db:migrate:local && pnpm db:seed:local
pnpm dev → :4321
# terminal 2 — dashboard. Same database, applies 0002 + 0003.
cd citerate-app
pnpm install
cp .env.example .env
pnpm db:migrate:local && pnpm db:seed:local
pnpm dev → :4322

Order matters once: the marketing repo's migration first, or 0002 has no tables to build on. Node 20.11+ and pnpm 9. Only value worth editing in either .env is SESSION_SECRET.

Every FAIL says what to run next — a missing table names the migration, an empty seed names the command, a leaking pane names the route and the status it returned.

THEN FOUR THAT NEED YOUR EYES
01
Sign in. Request a link on /sign-in, copy the URL from the dev console, open it. You should land in onboarding, not an empty dashboard.
02
Onboarding. Any domain works. Queries should arrive labelled crawl and category — category-only means the crawl step failed quietly.
03
Print a report. Open a seeded report and print to PDF. No clipped cards, no dark panels bleeding, footnotes intact. Locally this is the print path — Browser Rendering is production-only.
04
Client role. Sign in as the seeded client user: no billing, no settings, no second workspace anywhere in the nav.

pnpm preflight:local is the sibling check — it reads config rather than the running app, and warns if the shared database state is missing before you waste time on a failing server.

Q5 · WHEN CAN I HAND THIS TO CLAUDE CHAT
Now — but hand over the right thing

The code is complete and self-describing: two READMEs, three migrations, seeds, preflight, doctor. A fresh conversation can read all of it. Two honest limits, though.

GOOD FOR
Reading and explaining the code, reviewing copy, debugging a failing command from pasted output, writing a new page against the existing patterns, planning the scanner Worker.
NOT FOR
Running your terminal, deploying, or holding the whole 30-board design history in one conversation. A chat cannot see whether a command succeeded — you paste the output.

What to attach: the zip, or at minimum both README.md files, both wrangler.toml, and the Phase 11 runbook. Say which step of the runbook you are on — that single sentence saves a chat from guessing at context it cannot see.

My advice: keep design and visual work here where the boards and design system live; take deployment troubleshooting to a chat, since that is paste-the-error work and needs no history.
