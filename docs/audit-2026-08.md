# Citerate — code audit, August 2026

Full read of both repos: `citerate/` (marketing + scan engine) and `citerate-app/` (dashboard).
230 source files. Findings ordered by severity, each with the file and the fix.

**Overall:** the codebase is well above average for a pre-launch product. Tenant isolation is
consistently correct, secrets are handled properly, the SQL is uniformly parameterised, and the
scoring maths is right. The serious problems are concentrated in two places: the OTP path and
the scanner's public surface.

---

## Critical

### 1. Unlimited brute force on the 6-digit login code
`citerate-app/src/pages/api/auth/verify-code.ts`

`POST /api/auth/verify-code` has no attempt counter, no lockout, and no rate limit. `request-link.ts`
limits *issuing* tokens to 5/hour, but *verifying* is unbounded. The route loads up to five live
tokens for an email and tests the submitted code against all of them, so each guess gets up to five
chances against a 10⁶ space.

Anyone who knows a target's email address can trigger a token and then brute-force it. Within the
15-minute TTL this is a full account takeover, unauthenticated. This is the most serious issue found.

**Fix:** count failed attempts per email in the existing `RATE_LIMIT` KV binding — which is already
bound and unused on this route. Hard-fail after ~5, and consume/invalidate the token on repeated
failure. ~15 lines.

## High

### 2. Scanner's public `fetch` handler drains the job queue
`citerate/workers/scanner/index.ts:39`

The handler is documented as a "manual kick for local dev", but `scanner:deploy` ships it. It is
unauthenticated: any GET to the Worker's URL calls `drain(env)`, which claims jobs and calls the
paid engine APIs. A trivial loop against that URL spends the OpenAI/Perplexity/Gemini/SERP budget.

**Fix:** require a shared secret header, or restrict to `/health` and drop the drain path in
production.

### 3. Non-atomic job claim → duplicate observations and double spend
`citerate/workers/scanner/index.ts:62-85`

`SELECT ... WHERE status='pending'` then a separate `UPDATE ... SET status='claimed'`. Two overlapping
invocations — the every-minute cron plus any `fetch` hit — select the same rows and both process
them, producing duplicate `observations` and doubled engine cost. Finding 2 makes this trivially
reachable.

**Fix:** single-statement claim (`UPDATE ... WHERE id IN (SELECT ... LIMIT n) RETURNING *`), which D1
supports.

### 4. Protocol-relative open redirect after login
`citerate-app/src/pages/verify.ts:53`, `api/auth/verify-code.ts:64`

Both guard with `next.startsWith("/")`. `//evil.com` passes that check and browsers treat it as
`https://evil.com`. The redirect happens immediately after a session cookie is set, so it is a
credible phishing hop from a real Citerate magic link.

**Fix:** `next.startsWith("/") && !next.startsWith("//")`.

### 5. Auth guard fails open
`citerate-app/src/middleware.ts:27`

```js
if (!runtime?.env) return next();
```

If bindings are missing, every protected route renders with no session rather than failing closed.
Downstream pages then read `locals.user` as undefined. In dev the proxy always provides env, so this
only bites on a misconfigured deploy — which is exactly when you want it to fail closed.

**Fix:** return 503.

## Medium

### 6. Webhook replay window is unbounded
`citerate/src/pages/api/billing/webhook.ts:17`

HMAC verification is correct and constant-time, but `ts` is parsed and never compared against the
current time, and there is no dedup on event id. A captured valid webhook replays indefinitely —
against `subscription.created` that repeatedly re-grants a plan.

**Fix:** reject `ts` older than ~5 minutes; store processed event ids.

### 7. Free-scan progress reports up to 400%
`citerate/src/pages/api/scan.ts:126`, `workers/scanner/index.ts:232`

`scans.queries_total` is set to the query count (25). `queries_done` is incremented once per **job**,
and jobs are queries × engines. With 2 engines the bar reaches 200%; with 4 on a rescan, 400%.

**Fix:** set `queries_total` to `queries.length * engines.length`, or increment only when every
engine for a query has settled.

### 8. No UNIQUE constraint on `domains.hostname`
`citerate/migrations/0001_init.sql:74`

Only a plain index. `POST /api/scan` unconditionally inserts a new `domains` row, so every free scan
after the 24h cache expires creates a duplicate row for the same hostname. `requestJoin()` then does
`WHERE hostname = ? ... LIMIT 1` and picks an arbitrary one, so join requests can route to the wrong
workspace.

**Fix:** look up the existing domain before inserting; add a partial unique index.

### 9. Anyone with a share link can claim the domain
`citerate-app/src/lib/auth.ts:158`

`claimScan()` correctly refuses a scan already bound to another workspace, but an unclaimed one is
claimed by whoever gets there first. Free-scan share links are designed to be circulated publicly,
and there is no domain-ownership verification — so a competitor who receives a shared readout can
bind that domain into their own workspace.

**Fix:** require ownership verification (DNS TXT or the existing Search Console connection) before a
domain moves into a workspace.

### 10. KV rate limits are read-then-write
`citerate/src/lib/guard.ts:40`, `citerate-app/api/auth/request-link.ts:30`

Non-atomic, so a burst of parallel requests all read the same count and pass. The per-domain limit of
1/day is the main cost control on free scans, which makes this a spend risk, not just a hygiene one.

**Fix:** Durable Object counter, or accept and document the tolerance.

## Low

- **`assert()` in `rbac.ts:34` is dead and would not work.** It throws a `Response`, which Astro does
  not catch in API routes — it would surface as a 500, not a 403. Every actual call site correctly
  uses `can()` + `fail()`. Delete it before someone uses it.
- **`MATRIX[role]` throws on an unknown role** (`rbac.ts:31`). Any unexpected value in
  `memberships.role` produces a 500 rather than a denial. Default to no capabilities.
- **Fix owner is unvalidated** (`api/fixes/[id].ts`). `body.owner` is written to `owner_user_id`
  without checking workspace membership; `fixQueue()` then joins and returns that user's name and
  email. Minor cross-tenant leak, gated by having to guess a random id.
- **Rescan quota is racy and hardcoded.** The counter is checked, then written in a separate batch;
  and the `included` value on insert is a literal `10` regardless of plan.
- **Modulo bias** in `id()` (`db.ts:29`, `b % 36` over 0-255) and `sixDigitCode()` (`auth.ts:26`).
  Not exploitable — ids aren't secrets and the code's real weakness is finding 1 — but worth fixing
  alongside it.
- **`rid()` in the scanner produces variable-length ids** (`index.ts:19`) — no `padStart`, unlike
  `id()` in `db.ts`. Inconsistent, slightly higher collision odds.
- **Magic links are logged in plaintext** when email sending fails (`request-link.ts:47`). Correct
  and useful in dev; in production with a broken `RESEND_API_KEY` it writes working credentials to
  your log drain.
- **`gsap` is imported but not declared** (`src/scripts/modules/scroll-narrative.js`). Deliberate
  per the file comment, but it throws a Vite resolution error on every dev boot and will fail
  `pnpm build`. Either add it or stub the module.

## What is done well

Worth recording, because it is unusual at this stage:

- **Tenant isolation is consistent.** Every workspace-scoped route re-checks ownership in SQL rather
  than trusting a client id. `queryEvidence` is a good example: the route does an explicit ownership
  join before calling the helper.
- **The `cr_ws` cookie is not trusted.** `workspaceContext()` joins through `memberships`, so
  tampering with it cannot reach another workspace.
- **Sessions are correct.** 160-bit opaque token, only its SHA-256 stored, `httpOnly` + `secure` +
  `sameSite=lax`, separate TTL for untrusted devices, working "sign out everywhere".
- **All SQL is parameterised.** No string interpolation into queries anywhere in either repo.
- **The Wilson interval implementation is right** — see the separate positioning analysis for why
  `RUNS_PER_ENGINE = 3` is nonetheless a problem.
- **Secrets never touch the repo.** `.env.example` files carry safe defaults; production values are
  documented as `wrangler secret put`.

2. Findings 2 and 3 — the only ones that lose money.

5. The rest as normal work.
